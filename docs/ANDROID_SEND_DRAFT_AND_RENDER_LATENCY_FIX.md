# Android 发送草稿与聊天刷新卡顿修复

## 现状与目标

手机安装的是 `0.97.6-dev.1`（versionCode 401），仓库当前构建版本为 `0.103.12-dev.5`（409）。手机画面中一条已显示的用户消息曾同时留在输入框；当前画面已恢复为空。设备图形统计记录到主线程慢帧，当前聊天界面约有 1,158 个 View。

代码检查发现两条具体风险：回复中按钮优先执行暂停，即使输入框已有文字；HTTP 请求失败时一律恢复发送前的草稿，而服务端可能已经接收并发送了相同消息。发送确认、排队变更还会立即重建聊天列表，长聊天更容易卡顿。

本次属于修复 / PATCH，依次构建 `0.103.13-dev.1`（Android versionCode 410）到 `0.103.13-dev.7`（416）。目标是发送动作明确、已接受的消息不重新回到输入框，并减少发送阶段的整页重绘。

## 实施步骤

1. 输入框有文字或附件时，发送按钮执行发送或加入排队；输入框为空且正在回复时仍执行暂停。
2. 对连接中断等结果不明确的提交，用同一消息 ID 重试，利用服务端已有的幂等收据避免重复发送；明确拒绝才恢复草稿。持续无法确认时把待确认消息保存到 APP 私有目录，重启后恢复重试入口。
3. 发送确认和排队回执只更新或移除对应消息行，避免重建整个聊天列表；缓存输入框呼吸光晕的渐变和裁剪路径，减少逐帧分配；复用 HTTP 客户端和连接池，及时关闭失败响应；长对话首次只展示最近六轮，较早轮次仍可按原入口展开；用户滑动聊天时延后完整重绘至滑动停下。
4. 更新版本历史，构建独立 APK 并覆盖安装到手机；只做非发送式的画面与性能核对，不代替用户发送测试消息。
5. 检查变更并创建本地提交，不推送 GitHub。

## 验收条件

- 回复中有草稿时点击发送，草稿立即清空并作为消息提交或排队；空草稿时按钮仍可暂停。
- 服务端已接受消息但首次响应丢失时，重试不会重复发送，输入框不会恢复同一文本。
- 发送回执不触发整段历史重新布局；长聊天仍能滚动和输入。
- 无法确认送达时界面清楚标记，并允许使用同一消息 ID 重试。
